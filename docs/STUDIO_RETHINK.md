# Переосмысление DAYRIS Studio — концепция на согласование

Статус: интерактивный макет, не новая рабочая панель. Рабочий календарь, пользовательские данные, механизмы сохранения и выпуска не изменены. Макет: `docs/prototypes/dayris-studio-concept.html`, предназначен для просмотра внутри разговора.

## Почему нужна другая структура

Текущая мастерская объединяет несколько самостоятельных интерфейсов: настройки облачной админки, редактор локального оформления, конструктор расширений, карту исходников, вложенные диалоги и отдельные журналы. Даже работающие механизмы не дают одного устойчивого способа находить нужное действие. Добавление новых окон усугубляет проблему.

## Ориентир

PHP Devel Studio / классический RAD: проект, форма, объекты, свойства, события и код. Переносится принцип организации, не PHP, движок VCL и не неподдерживаемые старые исполняемые файлы. DAYRIS остаётся React/Vite/Supabase.

Первичные источники: [RAD-репозиторий семейства DevelStudio](https://github.com/devlephant/devleph), [Form Designer и Object Inspector](https://docwiki.embarcadero.com/RADStudio/Athens/en/Form_Designer_%28IDE_Tutorial%29), [синхронизация структуры, инспектора и дизайнера](https://docwiki.embarcadero.com/RADStudio/Athens/en/Structure_View_%28IDE_Tutorial%29). Wiki форка DevelStudio неполная: не выдавать предположения о точной раскладке старой версии за подтверждённую спецификацию.

## Одна локальная студия вместо набора админских страниц

- Слева: проект → экраны → элементы, отдельно оформление и исходники. Первым показывается смысловая структура, не все папки репозитория.
- Центр: вкладки «Дизайн / Код» для одного выбранного экрана. При смене режима объект не теряется. Один щелчок выбирает объект, двойной открывает его событие/код.
- Справа: постоянный инспектор с двумя вкладками «Свойства / События». В свойствах внешний вид, в событиях действия и обработчики. Из события открывается связанный исходник в центре, а не новая страница или вложенная модалка.
- Внизу: контекстная справка, изменения и журнал проверки. Справка хранится в проекте; рядом с незнакомым полем должны быть человеческое название, пояснение и путь к файлу, не ссылка «спросить ИИ».
- Сверху: одна последовательность «Сохранить → Проверить → Опубликовать» и история отмены. Сохранение локальное. Проверка запускает существующие фиксированные операции. Публикация — отдельное подтверждение выбранных файлов и результата сборки.
- Управление аккаунтами остаётся отдельной удалённой админкой, не частью конструктора интерфейса.

## Требования при последующем внедрении

1. Сохранить действующие RLS, роль Google-администратора, аудит правок и границы финансовых сущностей.
2. Повторно использовать локальный сервер с loopback/Origin/token, резервные копии и защиту от конфликтов. Не добавлять произвольный shell или выполнение вставленного JS в административной сессии.
3. Единый контекст выбранного экрана/объекта/файла и общий контракт сохранения; не просто вставить старые полные страницы в три колонки.
4. Свести `siteDesign.json`, собственную тему и расширения в один журнал изменений проекта. Разные типы данных остаются технически разными, но пользователь не должен выбирать между «облачным», «браузерным» и «локальным» сохранением.
5. Чётко различать «изменено в черновике», «сохранено на диск», «проверено», «отправлено в Git» и «выпущено на HTTPS». Не показывать push как подтверждённый deploy.
6. Нельзя обещать автоматическое перемещение произвольного React-узла между компонентами без соответствующей реализации. Для неподдерживаемого случая доступен точный исходник и понятная подпись ограничения.
7. Обязательный сценарий без ИИ: открыть проект → найти кнопку микрофона → изменить цвет → открыть событие → найти исходник → отменить → сохранить → проверить → подготовить выпуск. Отдельно: найти общий CSS и применить сезонный стиль.

## Уточнение: свободная песочница с окнами элементов

Новый ориентир пользователя — свободное поле с перемещаемыми окнами и связями, а не постоянный правый инспектор. Актуальный интерактивный макет: `docs/prototypes/dayris-workspace-canvas.html`. Предыдущий макет сохранён для сравнения.

- Календарь расположен на общем полотне. Выбор элемента открывает немодальное окно рядом; календарь остаётся доступным.
- Внутри окна — вид, логика/команды и связанный исходник. Линия показывает принадлежность окна элементу, а не придуманную зависимость исполнения.
- Незакреплённое окно заменяется при выборе нового элемента. Закреплённое остаётся открытым и по-прежнему перемещается за заголовок. Закрепление не блокирует координаты.
- Колесо масштабирует полотно относительно курсора; фон перетаскивается. Есть кнопки масштаба, «Всё в кадр», «Собрать окна», отмена и Ctrl+Z. На узком экране окна выстраиваются вертикально.
- В макете доступны изменение размера/цвета микрофона, демонстрационное добавление команды и сезонный стиль. Они не запускают реальные команды, не редактируют исходники и не публикуют приложение.

Следующий этап — согласовать поведение песочницы, затем перенести в неё реальные механизмы локальной студии. Обе демонстрации не публикуются на рабочий сайт до этого решения.
