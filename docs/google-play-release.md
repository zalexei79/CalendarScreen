## Предлагаемый путь

Упаковать опубликованную PWA через Bubblewrap / Trusted Web Activity. Это сохраняет браузерный вход Google и существующую веб-архитектуру. Выбор окончательно подтвердить после проверки рабочего HTTPS-домена и требований к DAYRIS PRO.

Нужны стабильный домен под управлением владельца и размещение `/.well-known/assetlinks.json`. Для Play в этот файл нужен SHA-256 сертификата **app signing** из Play Console; upload certificate сам по себе не подтверждает установленный из магазина пакет. Package ID выбрать до первого выпуска и затем сохранять.

При подготовке сборки проверить актуальное требование target SDK (на дату проверки API 36), versionCode, release signing, App Bundle и проверку Digital Asset Links. Секреты и ключи подписи не добавлять в Git. Проверить переходы Google и cTrader, возврат в приложение, кнопку назад, офлайн-режим и загрузку CSV на реальном Android.

## Проверка опубликованного сайта

19 сентября 2026: главная страница отвечает HTTP 200 по HTTPS; `/manifest.json` отвечает HTTP 200 с `application/json`, прежним названием приложения и иконками 192/512. `/.well-known/assetlinks.json` отвечает HTTP 404. Его нужно создать после выбора Android package ID и получения сертификата подписи; вымышленный fingerprint публиковать нельзя. Эти HTTP-проверки не подтверждают работу входа, платежей или мобильного интерфейса.

## Регистрация Google Play Console

Открыть https://play.google.com/console/signup под Google-аккаунтом будущего владельца. Выбрать тип аккаунта согласно реальному статусу владельца и требованиям Google к категории приложения. Регистрация стоит 25 USD однократно; ввод платёжных данных и проверку личности владелец проходит в интерфейсе Google. Публичный email поддержки не обязательно совпадает с Google-аккаунтом владельца. После регистрации выполнить показанные Console требования к проверке аккаунта и устройства.

Официальная инструкция: https://support.google.com/googleplay/android-developer/answer/6112435?hl=en-AU

## Подготовленный код оплаты

`src/features/pro/playBilling.mjs` — отдельный клиентский адаптер Digital Goods API / Payment Request API: получение товара, покупка, серверная проверка через переданную функцию, восстановление покупок. Он не подключён к интерфейсу и не меняет работающую веб-оплату. 8 тестов `tests/play-billing.test.mjs` проходят; тесты используют имитацию API, не реальную оплату Google.

Для подключения нужны Android package ID, настоящий ID товара в Play Console и серверная реализация проверки. `pro_monthly` в тестах — тестовый идентификатор, а не созданный товар. Существующий интерфейс предлагает помесячный DAYRIS PRO за $1.99; Android должен показывать реальные цену и условия из Play, включая локализацию и автоматическое продление.

Контракт функции `verifyPurchase({ productId, purchaseToken })`: возвращать `{ verified: true }` только после проверки Google API и сохранения результата на сервере. Сервер обязан проверить пользователя по JWT, использовать свой package ID и разрешённые товары, проверить состояние и срок подписки, исключить повторное присвоение токена другому пользователю, идемпотентно обновить доступ и подтвердить покупку. Клиентская успешная форма оплаты сама по себе не даёт DAYRIS PRO. Возвраты, отмены, продления и отложенные покупки требуют обработки серверных уведомлений и повторной сверки Google API.

Перед реализацией серверного моста получить актуальную схему DAYRIS PRO и определение `get_my_pro_status` из Supabase: в репозитории есть только клиентский вызов. Нельзя перезаписывать неизвестные правила реферального/административного DAYRIS PRO. До выпуска также подключить UI цены и восстановления, обработку отмен/ожидания и определение Play-канала после OAuth без перехода на Lemon Squeezy при недоступной Play Billing.

Основа API: https://developer.chrome.com/docs/android/trusted-web-activity/receive-payments-play-billing

## Обязательная работа до отправки

1. Проверить домен, manifest, HTTPS и корректность OAuth redirect URL на опубликованной версии.
2. Разобрать оплату: обычная продажа цифрового DAYRIS PRO в Play требует Play Billing, если не применяется разрешённое исключение/программа. TWA сама по себе не освобождает от правил. Для варианта без покупки убрать соответствующие предложения и переходы из Android-пути, включая косвенные ссылки; существующий серверный доступ DAYRIS PRO сохранить. Простого параметра в стартовом URL недостаточно без проверки OAuth и повторных запусков.
3. Реализовать удаление аккаунта в приложении и доступный снаружи веб-путь запроса удаления. Проверить полную схему Supabase, внешние связи и хранилища до реализации каскада; текущие миграции не описывают всю базу. Отзыв подключений cTrader, удаление пользовательских данных и очистку локального кэша проверить отдельно.
4. Подготовить и опубликовать политику конфиденциальности с реальными контактами, назначением обработки, получателями и сроками хранения. Не придумывать сроки удаления или заявления об отсутствии передачи данных.
5. Собрать подписанный AAB, настроить Digital Asset Links, проверить установку из внутреннего тестирования.
6. Сделать реальные скриншоты Android, иконку магазина и feature graphic; заполнить Data safety, доступ для проверки, возрастной рейтинг, рекламу и декларацию финансовых функций по фактическому поведению.
7. Если применимо, провести закрытое тестирование: новые личные аккаунты после 13.11.2023 — минимум 12 тестировщиков, непрерывно подключённых минимум 14 дней; затем подать запрос на production access. Это нельзя заменить локальными автотестами.
