# DAYRIS Admin: пользователи и визуальный редактор

Основной вход: `/admin.html`. Это отдельная точка входа с манифестом **DAYRIS Admin**, режимом `standalone` и собственным ID приложения. Старый адрес `/?admin=1` открывает редактор оформления. Панель адаптируется к телефону и ПК; Vite собирает оба HTML-входа.

В шапке календаря назначенного администратора есть кнопка **Admin / Админ-панель**. Её видимость подтверждается серверным `is_site_admin`, а не email из клиентского профиля. У обычных пользователей и гостей кнопки нет. Переход выполняется в той же вкладке на `/admin.html`, используя сессию календаря; повторный OAuth-вход не запускается. В iframe предпросмотра эта служебная кнопка не показывается.

## Управление пользователями

- Поиск по имени, email и UUID; страницы по 30 аккаунтов.
- Карточка пользователя: профиль, провайдеры входа, даты регистрации и последнего входа.
- Календарь по месяцам и дням. Итоги основного счёта, кошелька и планов раздельные, каждая валюта учитывается отдельно. Агрегация выполняется сервером по всем записям месяца и не зависит от пагинации списка.
- 24 раздела облачных данных: записи календаря, кошелёк, переводы, планы, заметки, активы/операции/оценки/расчёты капитала, настройки графиков и уведомлений, ценовые события, PRO, приглашения, интеграции, голосовые устройства/история, push-устройства и статусы доставки.
- Списки данных по 50 строк, выбор месяца/дня или всех дат, экспорт текущей страницы JSON с указанием пользователя, раздела, смещения и общего количества строк. Это постраничный экспорт, не полный архив аккаунта.
- По умолчанию — просмотр. Отдельный переключатель включает редактирование. Разрешены изменения записей календаря, операций кошелька и существующих дневных заметок.
- Причина изменения обязательна (5–500 символов). Сервер проверяет права и актуальность исходной записи, сохраняет значения до/после и администратора в одной транзакции с правкой. Если запись изменил пользователь или другой администратор, правка отклоняется без перезаписи.
- Для импортированных сделок разрешён только комментарий. Финансовые поля записей, связанных с расчётом продажи капитала, защищены и в календаре, и в кошельке.
- Журнал просмотров и изменений: общий и по конкретному пользователю, с пагинацией и раскрытием значений до/после.

Панель читает данные через проверяемые серверные RPC. Обычные RLS-политики таблиц пользователей не расширяются. Секреты cTrader/MetaTrader, хеши голосовых устройств и ключи Web Push исключены из ответов; реестр таблиц фиксирован. Управление ролями выполняется владельцем БД. Отдельного пароля нет: вход через Google, доступ — по назначенному UUID. Смена сессии на сессию пользователя, удаление аккаунтов и создание новых финансовых записей здесь не подключены.

Миграция `202610150003_admin_google_access.sql` закрывает и пользовательские RPC, и настройки оформления: для роли с `google_only=true` нужны подтверждённый Google-аккаунт, OAuth-метод в подписанном JWT и отсутствие альтернативных привязок входа. Пользователь не может назначить себе роль или обойти проверку изменением данных профиля. Анонимный локальный редактор на публичном URL больше не открывается.

Панель показывает синхронизированные облачные данные. Локальные дни рождения, настройки, сбережения и несинхронизированные записи с устройства пользователя не становятся доступны автоматически. Календарь в админке — административное представление этих данных, а не вход под чужой сессией.

## Редактор оформления

Рядом доступна вкладка **Проект**: карта рабочих папок, поиск по назначению, прямые связи импортов и локальный текстовый редактор с резервными копиями. Для предпросмотра исходников, сборки и подтверждённого commit/push запустите `npm run project:desk` и откройте локальный адрес. HTTPS-панель не получает возможность выполнять команды на ПК. Полная инструкция: [PROJECT_GUIDE.md](PROJECT_GUIDE.md). Секреты и служебные папки исключены; права на опубликованную админку не меняются.

- Реальное приложение в предпросмотре 390/1280 px с автоматическим масштабированием под окно ПК или телефона. «Редактирование» включено по умолчанию: нажатия выбирают ближайший зарегистрированный элемент с голубой рамкой, а не открывают дни/настройки. Нажатия вне зарегистрированных зон выбирают фон. Перехватываются также сенсорные жесты и клавиатурная активация. Вложенный предпросмотр пропускает повторный онбординг владельца, не меняя настройки обычного приложения.
- «Проверить приложение» включает настоящие действия аккаунта. Возврат в «Редактирование» после перехода по ссылке восстанавливает календарь. На телефоне кнопка «Параметры» переводит к настройкам выбранного элемента ниже предпросмотра.
- Раздельное оформление телефона (до 767 px) и ПК, копирование между ними.
- Фон календаря: цвет и изображение по HTTPS-ссылке или внутреннему пути. Акцент PRO подключён к переменной `--pro-gold`, а не ко всем существующим цветам приложения.
- Шапка, блок логотипа и названия, блок действий, кнопки установки, настроек, предыдущего/следующего месяца и «Сегодня», календарь, сетка и стиль всех ячеек дней.
- «+ Добавить кнопку»: до 20 собственных кнопок. Название, переход (внутренний путь от `/` или HTTPS) и расположение общие для устройств; оформление и видимость раздельные. Доступны зоны под шапкой календаря и закрепление внизу экрана. Можно удалить кнопку, отменить действие, сохранить в черновик и опубликовать. Без ссылки новая кнопка не выполняет переход. Публикация изменяет общий интерфейс пользователей, а не только календарь администратора.
- Размеры, цвет, скругление, смещение, видимость, порядок внутри существующего flex/grid-ряда. Переход по ссылке заменяет штатное действие зарегистрированной кнопки. Кнопка «Сегодня» видна только вне текущего месяца; установка — только в браузере.
- Отмена/повтор до 50 изменений, локальный черновик, импорт/экспорт JSON.
- Облачный черновик, публикация, последние 20 публикаций в интерфейсе, восстановление старой версии в черновик с последующей публикацией.
- Сохранение и публикация проверяют версию черновика, чтобы два устройства не перезаписали друг друга молча. При конфликте экспортируйте изменения, затем перезагрузите редактор.
- Приложение запрашивает опубликованное оформление при открытии, возвращении во вкладку и раз в минуту. Если облако недоступно, используется исходный дизайн. Офлайн-кэш конфигурации пока не подключён.

Параметры применяются только к зарегистрированным элементам. Произвольные CSS, JavaScript и обработчики из конфигурации не выполняются. Редактор, чтение черновика и запись доступны только назначенному администратору после проверки Google-входа. Предпросмотр — настоящее приложение с текущей сессией: при отключённом выборе элементов действия могут изменять данные аккаунта.

## Подключение облака

1. Примените по порядку миграции `202610150001_site_admin.sql`, `202610150002_admin_user_management.sql`, `202610150003_admin_google_access.sql` из `supabase/migrations` к нужному проекту Supabase обычным способом миграций. Требуется роль владельца БД.
2. Назначьте существующий аккаунт администратором через доверенный SQL Editor. Используйте UUID из Authentication → Users, не случайное значение и не публичные метаданные пользователя:

```sql
insert into public.site_admins(user_id)
values ('UUID_ВАШЕГО_АККАУНТА')
on conflict (user_id) do nothing;

-- Просмотр пользовательских данных и право исправлять разрешённые записи:
update public.site_admins
set can_view_users = true, can_edit_users = true, google_only = true
where user_id = 'UUID_ВАШЕГО_АККАУНТА';

-- Для сотрудника поддержки только с просмотром: can_edit_users = false.
```

3. В Supabase Authentication → URL Configuration проверьте, что точный адрес `https://ВАШ-ДОМЕН/admin.html` или уже существующее правило вашего домена разрешено для OAuth redirect. Панель входа предлагает Google и возвращает на `/admin.html`; провайдера заново настраивать не требуется, если Google уже работает в DAYRIS.
4. Войдите этим аккаунтом в DAYRIS Admin. Проверьте чтение реального тестового аккаунта, изменение тестовой записи и журнал. В разделе оформления проверьте облачное сохранение, публикацию и отображение в отдельной обычной вкладке.
5. Проверьте обычным аккаунтом и администратором с правом только просмотра, что закрытые RPC отклоняются. Проверьте отзыв разрешений. Локальные PostgreSQL-тесты подтверждают поведение на тестовой схеме, но не применение миграций в production.

Права задаёт закрытая таблица `site_admins`. Браузер не может назначать администраторов; ключ service role не нужен в клиенте. Конфигурация опубликованного дизайна общедоступна и не должна содержать секреты. История публикаций хранится в БД; интерфейс показывает последние 20.

## Установка отдельного приложения

Откройте именно `/admin.html` по HTTPS. На ПК используйте кнопку «Установить приложение» или установку через меню Edge/Chrome; приложение будет открываться отдельным окном. На Android — установку через меню браузера. На iPhone/iPad — Safari → Поделиться → На экран «Домой». На старом адресе `/?admin=1` кнопка сначала открывает правильный HTML-вход, чтобы не установить обычный DAYRIS вместо Admin.

Это устанавливаемая PWA, не отдельный EXE/APK. Манифесты имеют разные ID и точки старта; сессия авторизации остаётся общей в рамках origin там, где браузер разделяет хранилище. На iOS установленное приложение может потребовать отдельный вход. Для пользовательских данных необходим интернет. HTML-оболочка админки кэшируется отдельно и не подменяет оболочку календаря; API-ответы пользователей не кэшируются service worker.

Физическая установка на телефон/ПК и поведение OAuth в установленной PWA должны проверяться после публикации на HTTPS-домене. Локальная сборка и headless-браузер не подтверждают фактическую установку.

Правила идентификации приложений и границ окна: [MDN: manifest id](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/id), [MDN: manifest scope](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/scope).

## Следующие очереди полной панели

1. Регистрация остальных экранов и элементов: календарь, ввод записей, кошелёк, капитал, PRO, настройки, онбординг. Для каждого элемента — стабильный ID, допустимые параметры и доступные действия.
2. Библиотека изображений с загрузкой, ограничениями файлов и политиками Storage; отдельные изображения для телефона и ПК.
3. Перемещение существующих элементов между разрешёнными зонами, изменение сетки и порядка разделов. Рамки выбора и две зоны для новых кнопок уже подключены; свободный перенос произвольных React-компонентов требует отдельной модели layout.
4. Реестр штатных действий кнопок и внутренних экранов, редактирование подписей по языкам. В текущей версии можно назначить ссылку; произвольное действие другой кнопки выбрать нельзя.
5. Создание записей, управление доступом PRO, отправка уведомлений, управление подключениями и полный архив аккаунта. Сейчас эти разделы можно просматривать; изменения финансовых записей описаны выше.
6. Управление ролями из панели, подтверждение публикации оформления, аудит публикаций в общем журнале, отдельный демонстрационный аккаунт для интерактивного предпросмотра.

## Проверка

`node --test tests/site-config.test.mjs`

`node --test tests/admin-users-db.test.mjs tests/admin-users-model.test.mjs` — реальная PostgreSQL-реализация в PGlite, локальные миграции, RLS/RPC, права просмотра и редактирования, изоляция владельцев, исключение секретов, агрегация валют, защита импортов и связанных расчётов, конфликты и атомарность журнала. Использует ранее установленный тестовый PGlite из `android/app/build/widget-sql-test`; другой путь можно задать через `DAYRIS_PGLITE_PACKAGE`.

`node --test tests/admin-service-worker.test.mjs` — раздельное кэширование оболочек, исключение API из кэша и разные идентификаторы установки.

`npm run build`

`node tests/site-admin-ui-check.mjs` — локальная production-сборка в headless Edge, тестовая сессия и подменённые сетевые ответы. Проверяет реальный iframe, применение опубликованного дизайна в обычном приложении, сохранение/публикацию по протоколу, блокировку кнопок для неадминистратора и отсутствие горизонтального переполнения панели на 390 px. Не заменяет проверку RLS в Supabase.

`node tests/admin-users-ui-check.mjs` — браузерный сценарий: отдельный HTML-вход/манифест, календарь выбранного пользователя, явный режим редактирования, привязка изменений к выбранному аккаунту, причина и журнал, режим только просмотра, переключение пользователей, отказ в загрузке без прав и мобильный layout. API подменён тестовыми ответами.

Старый дополнительный сценарий `tests/voice-conversation-app-ui-check.mjs` обновлён для имён общих assets многовходовой сборки, но его гостевая fixture останавливается на существующем экране входа DAYRIS до календаря. В этой задаче голосовая логика не менялась; успешное прохождение этого сценария не заявляется.

Перед релизом отдельно нужны применение миграции, проверка RLS/RPC двумя аккаунтами и проверка на телефоне. Само наличие SQL-файла не означает, что облачная админка подключена.
